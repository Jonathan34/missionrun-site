mmissionrun

Delegate your backlog to a crew of AI coding agents, behind gates you control.

Point missionrun at a repository and say what you want done. A crew of roles (a researcher, an engineer, a reviewer) works through it in missions, on your Mac, with the Claude Code, Codex or Gemini CLI you already pay for. Each agent session runs in its own sandbox, and nothing reaches your branches or other people until you approve it.

Coming soon · open source, Apache-2.0

The problem

Coding agents are powerful. Running them all day is a job of its own.

An agent can fix a bug or bump a dependency well. The hard part is everything around it.

A backlog that never shrinks

Outdated packages, open bugs, docs that drifted, tests nobody wrote. Each one is small. Together they never get done, because something is always more urgent.

Agents that need babysitting

One terminal per agent, one prompt at a time. You restate the context, watch the output, pass it to the next tool, and remember what was already tried. The agent works; you coordinate.

The fear of letting go

Letting an agent push, open pull requests or merge unattended is a leap. Most tools offer all or nothing: watch every step, or hand over the keys.

missionrun turns that backlog into long-lived missions a crew works on its own, and puts a gate you control in front of every action that reaches your branches or other people.

Typical use cases

Pick a mission, or describe your own

These come from the mission templates that ship with missionrun. A mission can keep going for as long as you like, or stop once its goal is met.

Keep dependencies secure

Checks your code and packages every day for known security problems and outdated dependencies, and fixes them one small change at a time.

You need: nothing to set up. Label a GitHub issue security and it works on that too.

"Keep our npm packages free of known vulnerabilities."

Fix bugs from GitHub issues

Works issues labelled bug, FIXME notes in your code, and what its own daily check finds.

You need: nothing to set up. Label an issue bug and it picks it up.

"Fix the crash when a recipe has no photo."

Keep docs in sync

Every Monday, finds what last week's code changes made wrong in your documentation, and fixes just that. If nothing is out of date, it says so.

You need: your documentation under docs/.

"The setup guide still says Node.js 18."

Raise test coverage

Finds the code your tests don't cover and writes the tests it needs, area by area, until your target is met. Or keeps coverage there, checking every week.

You need: a command that reports coverage, such as vitest --coverage. The target is 80% unless you say otherwise.

"Get the parser to 90%."

Keep a learning resource current

Keeps a course, a tutorial or your notes up to date: it checks what has changed since, and corrects or adds a few things at a time, in the material's own voice.

You need: the material in a folder, and anything it must never change.

"Refresh the model names, keep the chapter order."

Hold a performance budget

Keeps one thing fast. It times it with your own benchmark and fixes the regression when it gets slower than your budget.

You need: a command that measures it, such as npm run bench, and a budget, such as 200 ms.

"Keep the search page under 200 ms."

Other templates write release notes each week, research a topic, upgrade a framework, run an accessibility pass, or build an app from one sentence.

How it works

From a repository to a merged change, in five steps

You set the direction and make the calls. The crew does the work in between.

  1. Point at a repo

    A local folder, an owner/name or a GitHub URL. missionrun clones it with your own gh login when it needs to.

  2. Say what you want

    Pick a mission or write a sentence. An agent drafts a mission brief from the repo and your words, and asks what it could not work out, with a suggested answer for each.

  3. The crew works in missions

    A mission watches its sources: issues, TODO markers, a daily check, a schedule. The crew works each new item in its own git worktree, every agent in its own sandbox.

  4. You approve at the gates

    What needs you waits in one list: an approval, a question, a merge. Each decision is in words, and every button says what it does before you press it.

  5. It lands

    missionrun merges into your branch, pushes, or opens the pull request itself, with your own git and gh credentials, and only after the gate.

Autonomy, one kind of action at a time

Every kind of outward action has its own switch: merge, push, open a pull request, open an issue, comment, label, post publicly, and approve outputs. Each one starts on Ask me.

  • After a clean run of changes, missionrun suggests letting that one kind go Automatic. It never switches by itself.
  • Switch any row back at any time. A revert makes it suggest asking again.
  • Every choice is recorded, and once a daily token or dollar budget is spent, the mission starts no new work.

Architecture

Everything runs on your Mac

A native app, a local database, and the agent CLIs you already have, each fenced in its own sandbox. GitHub is reached only through your own gh, after the gate.

  • missionrun app: a Tauri desktop shell with a React interface and a Rust runtime (core, application, infrastructure and runtime crates) that runs missions, the scheduler and the gates.
  • SQLite store: a local database of missions, runs, approvals and an append-only history, so a run can resume after a restart. Keys you paste stay in the macOS Keychain.
  • Agent sessions: Claude Code, Codex CLI or Gemini CLI, run as themselves, each session inside its own deny-by-default Seatbelt sandbox. Each role in a crew can use a different CLI and model.
  • Git worktrees: each run works in its own worktree of your repository, so your checkout is left alone until you merge.
  • Approval gate: merges, pushes, pull requests, issues and comments wait for you, unless you made that one kind Automatic.
  • GitHub through gh: missionrun, not the agent, opens pull requests and issues with your own login, after the gate.
  • Model providers: each CLI talks to the model it already signs in with: a subscription, an API key, a cloud account or a local model.
  • Headless server (optional): the same backend without the desktop shell, serving the web interface on 127.0.0.1 from the same store.

Local-first

No missionrun account and no missionrun server. State lives in a SQLite file on your Mac, and missions work on your repositories where they are.

Your own CLIs

missionrun drives the agent CLIs you already use, signed in the way you already pay. Agents never hold your publishing credentials.

Gates on everything outward

Anything that reaches your branches or other people waits for an approved proposal, or for the one switch you set to Automatic.

FAQ

Questions

Is it free?

Yes. missionrun will be open source under the Apache-2.0 licence, with no account. You pay only for the agents you already use, on your own plan or key.

Which agents does it work with?

Claude Code, Codex CLI and Gemini CLI, run as themselves. Each signs in the way you already pay: a subscription, an API key kept in the macOS Keychain, a cloud account, a local model through Ollama, or the setup that already works in your terminal.

Does it send my code anywhere?

Only where you point it. Your code goes to the agent CLIs you configure (and through them to the model they sign in with), and to GitHub only when you approve a push, a pull request or a comment, or set that kind of action to Automatic. There is no missionrun server.

Is it macOS only?

For now, yes: macOS 13 or later on Apple Silicon (M1 or later). The per-session sandbox is built on macOS Seatbelt.

When can I try it?

Soon. missionrun is getting ready for its first public release; there is nothing to download yet.
